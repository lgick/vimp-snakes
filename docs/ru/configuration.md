# Конфигурация (игра-плагин)

Эта страница — о собственной конфигурации `vimp-snakes`, игровой половине
контракта, описанного в движковом
[plugin-api.md](https://github.com/lgick/vimp-engine/blob/main/docs/ru/plugin-api.md).
Конфигурация самого движка (env-переменные, `hostDefaults`, конфиг
мастера/лобби, порты/опкоды) — в движковом
[configuration.md](https://github.com/lgick/vimp-engine/blob/main/docs/ru/configuration.md).

`src/config/game.js` (host-половина) и `src/config/client.js` (клиентская)
отдаются движку через `HostPlugin.gameConfig` и
`HostPlugin.buildClientGameConfig()`; `src/config/auth.js` — через
`HostPlugin.authSchema`; `src/config/sounds.js` и `src/config/snapshot.js`
питают клиентский конфиг и кодек снапшотов соответственно.

После каждой правки здесь запускайте `npm run check:contract`: движок
проверяет на старте всего девять путей, остальное читает лениво — поэтому
опечатка всплывает чёрным канвасом, а не ошибкой.

## src/config/game.js — игровой конфиг

Импортирует карту, модель змейки, (пустую) таблицу оружия и схему снапшота из
`src/data/` и `src/config/`.

### Основные параметры

| Параметр | Значение | Описание |
| --- | --- | --- |
| `title` | `'Vimp Snakes'` | Показывают лобби и экран авторизации |
| `parts.models` | `src/data/models.js` | Классы змеек; дословно уходит в оба ядра |
| `parts.weapons` | `{}` | Оружия нет — путь проверяется на старте, поэтому существует и пуст |
| `parts.friendlyFire` | `false` | Такого правила тоже нет; проверяется, поэтому объявлен |
| `snapshot` | `src/config/snapshot.js` | Раскладка провода |
| `maps` / `currentMap` | `{ arena }` / `'arena'` | Единственная карта |
| `mapScale` | `1` | Масштабирующий проход движка — копия |
| `mapSetId` | `'c1'` | Запасной ключ снапшота для карты без своего |
| `mapsInVote` | `1` | Голосовать не за что, но ключ читается |
| `soundCues` | все пять `null` | Каждое движковое событие завязано на раунды и убийства, которыми игра не пользуется |
| `playerState.defaultState` | `{ best: 0, eaten: 0 }` | Стартовый профиль на auth-сервисе — непрозрачен движку, пишет его `StatBridge` |
| `noSpectators` | `true` | Одна команда, вошедший сразу в ней, голосования на входе нет |
| `endlessRound` | `true` | Движок сам не перезапускает раунд и не чистит таблицу |
| `teams` | `{ players: 1 }` | Ровно одна команда — требование `noSpectators` |
| `scripted` | `namePrefix: 'Snake', defaultModel: 's1'` | Имена и класс ботов |
| `roomDefaults.maxPlayers` | `32` | Потолок комнаты, публикуется в манифесте; карта обязана его вместить |
| `roomForm` | `maxPlayers`, `map` | Форма создания комнаты в лобби. `roundTime`/`mapTime`/`friendlyFire` отсутствуют намеренно |

`timers` сливается с движковыми `hostDefaults` **поверхностно**, поэтому его
переопределение перечисляет каждый ключ заново. `roundTime` и `mapTime`
прибиты к `roomTimeMax` (час): при `endlessRound` истёкший таймер раунда не
делает ничего, но ячейка времени на панели отсчитывает именно от него.
`timeStep` — `1000/120`, и трогать его нельзя: шаг ядра берётся из движковых
`hostDefaults`, поэтому правка здесь рассинхронизирует цикл Worker'а с
симуляцией.

### Статистика (`stat`)

Четыре колонки, сопоставляемых с `client.js` позиционно: `name` (0),
`status` (1), `score` (2), `latency` (3). `name` и `latency` — движковые и
обязаны сохранить имена; `status` тоже движковая (`RoundManager` пишет туда
`''` при допуске игрока).

Единственную игровую колонку — `score` — пишет **эта игра**
(`src/host/StatBridge.js`), а не движок, и несёт она `bodyMethod: '='`
(замена), а не `'+'` (накопление): мост сам ведёт итог, поэтому повторно
присланное значение безвредно, а потерянное само чинится следующим событием.

Колонки `rank` **больше нет**: по `Tab` клиент показывает не эту комнату, а
глобальный дневной топ-10 игры, который забирает сам (см. `modules.stat`
ниже). Остальная схема всё равно остаётся — движок продолжает писать `name`,
`status` и `latency` в свою таблицу, и удаление колонок сломало бы эти пути.
`deaths`, `eaten` и `kills` отсутствуют намеренно.

### Профиль игрока (`playerState`)

Движок держит `state` непрозрачным JSON; эта игра хранит `{ best, eaten }` —
лучший счёт ОДНОЙ жизни за всю историю и пожизненное число кристаллов, —
записываемые `StatBridge._recordBest` на каждой смерти.

Сами рейтинги здесь не хранятся. Одна жизнь — одна игра: мост сообщает её
результат через `vimp.addPlayerPoints(gameId, score)` +
`vimp.finishPlayerGame(gameId)` и затем *просит* запись
`vimp.flushPlayerData({ urgent: true })` — дневной рекорд, месячная сумма и
итог за всё время это движковая раскладка того одного числа, и как часто оно
доходит до базы, решает тоже движок (см.
[gameplay.md](gameplay.md#результат-игры)).
Механика синхронизации движковая —
[auth.md](https://github.com/lgick/vimp-engine/blob/main/docs/ru/auth.md#rank-and-state-loading-and-sync-host).

### Панель HUD (`panel`)

`fields` — host-поля с коротким проводным `key` и стартовым значением:
`crystals` → `c` (что змейка несёт), `score` → `s` (единственная видимая
ячейка), `dead` → `d` (0 живая, `crystals + 1` мёртвая — значения панели
обрезаются снизу нулём, поэтому «мёртв без груза» требует этой единицы).
`activeKey: 'wa'` — движковая ячейка «активное оружие», куда ядро пишет
`CRUISE`/`BOOST`; оставить её `null` значит разослать всем клиентам литеральный
ключ `'null'`.

Ключ `t` (время раунда) — движковый и здесь объявляться не должен, но клиент
обязан объявить для него поле `type: 'time'`.

### Клавиши (`playerKeys`)

| Действие | Бит | Тип |
| --- | --- | --- |
| `left` | `1 << 0` | удержание |
| `right` | `1 << 1` | удержание |
| `boost` | `1 << 2` | удержание |
| `respawn` | `1 << 3` | `type: 1` — одноразовая, потребляется ровно одним фиксированным шагом |

Каждое имя отсюда обязано иметь клавишу в `keySetList[1]` (`client.js`), иначе
нажать его нельзя. Ни газа, ни тормоза нет: змейка всегда движется.

## src/config/client.js — клиентская половина CONFIG_DATA

Отдаётся через `HostPlugin.buildClientGameConfig()`, движок сливает её со
своими `clientDefaults.js` (рекурсивно — поэтому отключение движкового ключа
означает перекрытие, а не удаление).

### `parts` — игровые сущности

- **`gameSets`** — ключ снапшота (или `setId` карты) → классы частей:
  `s1: ['Snake']`, `cr: ['Crystal']`, `c1: ['Arena']`. Ключ без записи — это
  чёрный канвас.
- **`entitiesOnCanvas`** — класс части → канвас; это **единственная**
  регистрация у фабрики. Все три части живут на `vimp`.
- **`bakedAssets`** — две записи, обе пекутся **белыми** один раз на канвас
  при старте, а часть их тонирует и масштабирует: пекарь `crystalGem` рисует
  самоцвет (радиус 32, 6 граней), поэтому каждый тир и цвет — это `tint` и
  `scale` одной текстуры и шестьдесят кристаллов остаются одним батчем; пекарь
  `crown` рисует знак месячного топ-10 (размер 64, 3 зубца). Печёного ассета
  нет у ТЕЛА змейки: это обводка пути, ширина которой каждый кадр следует за
  числом кристаллов.
- **`componentDependencies`** — только движковые сервисы, и все три идут
  `Snake`: `soundManager` (звук подбора змейка играет только для игрока *этой*
  вкладки — тридцать одновременно жующих змеек это стена шума), `localPlayer`
  («моя ли это змейка?») и `accolades` («какое место у этой змейки в
  глобальном топе игры?» — часть спрашивает на отрисовке и рисует ромбы
  дневного топ-10 или корону месячного). `accolades` — пятый сервис движкового
  пула, ему нужен `ENGINE_API_VERSION` 4.

### Канвас и камера

Один канвас, `vimp`: 960×600 при 16:10, `baseScale '1:1'` (при дизайн-ширине
видно ~1920 из 2560 единиц арены — граница это то, к чему подъезжаешь, а не
рамка, которую видно всегда), `dynamicCamera: true`, `shakeCamera: false`
(`CoreEvent::Shake` в игре не эмитится).

### `modules.controls`

- **`modes`** — `77: ''` обезвреживает движковое меню голосования (`m`).
  Дефолты сливаются рекурсивно, поэтому ключ надо **перекрыть**; удаление
  оставило бы движковое значение, и меню продолжало бы открываться пустым.
- **`keySetList`** — `[0]` наблюдатель (`n`/`p`, в этой игре недостижим),
  `[1]` игрок: `65: left`, `68: right`, `87: boost`, `82: respawn`. Каждое
  действие обязано быть ключом `gameConfig.playerKeys`, и наоборот.
- **`pointer`** — `keySets: [1]`, `doubleTapMs: 300`, `doubleTapPx: 40`,
  `sendIntervalMs: 50`. Движок шлёт канал указателя только играм, объявившим
  этот ключ, и только в перечисленных наборах клавиш.

### Тексты и схемы

- **`chat.params.messages`** — тексты кодов системных сообщений по группам.
  Группы `s`/`v`/`m`/`c`/`n` движковые, `g` — этой игры
  (`src/host/systemMessages.js`: `BOTS_SET`, `BOT_COUNT_INVALID`). Часть
  движковых текстов здесь недостижима, но **индекс внутри группы и есть код**
  — выбросив один, вы сдвинете все последующие на чужие события, поэтому они
  остаются, переформулированные под эту игру.
- **`panel`** — проводной ключ → имя поля и список полей, **порядок которого и
  есть порядок ячеек**. Видна только `score`; остальные объявлены, потому что
  контракт панели требует назвать каждое host-поле, и скрыты в `style.css`.
- **`stat`** — `mode: 'leaderboard'`: по `Tab` показывается глобальный топ
  игры, а не таблица комнаты, поэтому список клиент забирает у мастера сам, а
  хост не шлёт для него строк. `period: 'day'` (лучший результат одной игры за
  сутки UTC), `limit: 10`, `refreshMs: 15000` и три колонки — `#`, `snake`,
  `score`. Порядок приходит из auth, поэтому `heads`, `bodies` и `sortList`
  ушли: сортировать нечего и команды в глобальном списке нет. Игрок вне топа
  заменяет собой десятую строку. Режиму нужен `ENGINE_API_VERSION` 4, а
  движок рисует для него лишь голый скелет `.stat-leaderboard` — оформление
  это игра (`src/client/style.css`).
- **Модуля `vote` нет вовсе** — см.
  [gameplay.md](gameplay.md#чего-в-этой-игре-нет).
- **`gameInform.list`** — `'{0} WINS!'`, `'SLITHER!'`, `'GAME OVER!'`; индексы
  фиксированы движком (winnerTeam, roundStart, gameOver).

## src/config/auth.js — форма авторизации

Экран входа, который движок рисует перед подключением игрока. Здесь живут три
ловушки, и каждая уже стоила отладочной сессии в реальной игре:

- id контейнера — `fieldsId`, а **не** `formId`: движок резолвит неверный ключ
  в `null`, и экран падает с TypeError на первом рендере;
- поля ника **нет** — идентичность приходит из лобби по JWT;
- поле модели обязано называться ровно **`model`** — движок читает
  `params.model`, создавая участника.

`validators` — это функции, они не сериализуются клиенту и выполняются на
хосте, когда приходит ответ (`isValidModel`). Экран показывается **один раз** —
пути назад у движка нет, поэтому экран после смерти — собственный оверлей игры
(`src/client/gameOver.js`).

## src/config/sounds.js — каталог звуков

Два звука: `pickup` (приоритет 80, громкость 0.35) и `death` (150, 0.5), оба
играются частями позиционно через `soundManager`. Каждая запись обязана
поставляться **парой webm + mp3** — клиент идёт по `codecList` и берёт первый
поддерживаемый кодек, поэтому отсутствие `.mp3` ломает только Safari. Никогда
не задавайте `path`: движок перезаписывает его на `${assetsBase}sounds/`.

## src/config/snapshot.js — схема ключей снапшота

Три блока — `s1`, `cr`, `c1` — описаны в [core.md](core.md#кадры). Два правила
при правке:

- **порядок полей позиционно связан** со `SnakeRow`/`CrystalRow` в
  `core/src/game.rs`; соответствие ничем не проверяется, поэтому перестановка
  двух записей здесь без такой же перестановки там даёт мусор, а не ошибку;
- `SPINE_POINTS = 16` экспортируется отсюда и продублирован в
  `core/src/motion.rs` и `src/client/parts/Snake.js`; сверяет их
  `tests/config/contract.test.js`.

## src/data/ — игровые данные

### models.js

Один класс змейки, `s1`. Ключ — имя модели: это и ключ блока снапшота, и
значение поля `model` формы авторизации, и `gameConfig.scripted.defaultModel`.

| Группа | Поля |
| --- | --- |
| движение | `baseSpeed` 260, `boostFactor` 1.9, `turnSpeed` 3.4, `turnSpeedFalloff` 0.18, `turnSpeedMin` 1.4 |
| тело | `baseRadius` 14, `radiusGain` 1.6, `baseLength` 150, `lengthPerCrystal` 9, `pointSpacing` 6 |
| ускорение | `boostDrainPerSecond` 6, `boostMinCrystals` 2 |
| `world` | `maxCrystals` 60, `spawnInterval` 0.35, `tierWeights` `[70, 25, 5]`, `tiers` (из `palette.js`), `dropRatio` 0.8, `edgeMargin` 60, `startCrystals` 0, `spawnGraceSeconds` 2 |

**Почему правила мира лежат внутри модели**: половину `game` из init JSON
собирает движок из фиксированного набора полей (`friendlyFire`, `models`,
`weapons`, `playerKeys`, `panel`), а произвольный ключ `parts.*` доходит до
клиентского конфига и никогда до ядра. При ровно одном классе змейки вложить
правила арены и поля кристаллов в него — единственное место, откуда их могут
прочитать оба ядра.

### palette.js

`SNAKE_COLORS` (12) и `CRYSTAL_COLORS` (6) — ядро не видит цвета, оно
разыгрывает **индекс** и шлёт его как `u8`. **Дописывать, никогда не
вставлять**: индекс и есть идентичность, поэтому цвет, вставленный в середину,
перекрашивает всех уже уехавших на провод змеек. Здесь же `CRYSTAL_TIERS` —
`value` это и получаемые кристаллы, и начисляемые очки, `radius` это и радиус
подбора, и рисуемый размер; `models.js` импортирует массив, чтобы ядро
начисляло ровно за то, что рисует клиент.

### theme.js

Вид арены (`ARENA`: фон, пол, граница и её толщина, концентрические кольца) и
змейки (`SNAKE`: внутренняя обводка, сглаживание Catmull-Rom, цвета глаза и
зрачка, свечение ускорения). Импортируется частями **напрямую**, не через
конфиг: объект `gameConfig.parts.arena` до части не дойдёт, а названный в
`dependencies` молча окажется `undefined`.

### maps/arena.js

Единственная карта и единственный файл игры, знающий размер. Экспортирует
**функцию**: `buildArena(count)` отдаёт объект карты для комнаты на `count`
участников, а дефолтный экспорт (`buildArena(0)`) — то, что
`scripts/export-maps.js` пишет в `dist/maps/arena.json`.

| Константа | Значение | Смысл |
| --- | --- | --- |
| `STEP` | 128 | мировых единиц на клетку |
| `BASE_SIZE` / `BASE_PLAYERS` | 20 / 8 | размер, под который игра настроена (2560 в ширину, радиус 1280) |
| `PLAYER_STEP` | 4 | население округляется вверх до кратного перед вычислением размера |
| `RESPAWN_COUNT` | 64 | жёсткая вместимость команды на этой карте — намеренно вдвое больше `maxPlayers` |
| `RESPAWN_SPAN` | 0.72 | как далеко может стоять самая внешняя точка респавна |
| `RESPAWN_FAN_DEG` | 25 | насколько курс на спавне может отклоняться от «строго в центр» |

`arenaSizeFor(count) = round(BASE_SIZE * sqrt(max(stepped, 8) / 8))`.
Респавны — спираль подсолнуха (`GOLDEN_ANGLE`, радиус через `sqrt`, чтобы
точки были равномерны по **площади**), обходимая в порядке **обращённых
битов**, поэтому любой префикс последовательности покрывает весь диск, а не
кучкуется в середине; из-за этого `RESPAWN_COUNT` обязан оставаться степенью
двойки, и файл бросает исключение при импорте, если это не так.

`layers` не должен быть пустым, хотя из плиток ничего не рисуется: движок
строит части карты, итерируя его, поэтому `layers: {}` означает, что часть
`Arena` никогда не будет создана и канвас останется чёрным. `physicsStatic`
**пуст** намеренно: запись там превратила бы каждую клетку в статический
коллайдер и заполнила диск камнем.
