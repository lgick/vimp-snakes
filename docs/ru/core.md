# Rust-ядро игры (core/)

`vimp-snakes-core` — симуляция этой игры поверх движкового crate
`vimp-engine-core`. Собирается в WASM дважды — сборка для браузера/Worker'а
(`core/pkg-web/`) и Node-сборка (`core/pkg-node/`, для тестов и headless-
раннера) — и экспортирует ровно два класса:

| Класс | Где живёт | Чем владеет |
| --- | --- | --- |
| `GameCore` | Web Worker хоста комнаты | авторитетный матч |
| `ClientCore` | вкладка каждого игрока | интерполяция (движок) + предсказание локальной змейки (этот crate) |

Всё, что движок у них вызывает, генерируют две ABI-макросы —
`export_game_core_abi!` и `export_client_core_abi!`, — поэтому в
`core/src/lib.rs` руками написаны только конструкторы и два игровых
клиентских метода. Общий контракт — движковый
([05-wasm-core.md](https://github.com/lgick/vimp-engine/tree/main/docs/ai)); эта
страница о том, что кладёт внутрь него *эта* игра.

**Модуля физики нет, тегов тел нет.** Змейка — ломаная, и всё, что может её
убить, — проверка расстояния. Rapier-мир движка создаётся и шагает, но пуст.

## Структура

```
core/src/
  lib.rs        — два экспортируемых класса, разбор конфига, ABI-макросы
  config.rs     — половина `game` из init JSON: SnakeConfig, WorldConfig,
                  CrystalTier, KeyConfig, ключи панели; валидация
  motion.rs     — ОБЩАЯ математика: step_angle, speed_of, advance_head,
                  radius_for, length_for, turn_speed_for, BodyPath
  snake.rs      — одна змейка: зажатые клавиши, тело, step(), respawn(),
                  spawn-grace, prediction_state()
  game.rs       — авторитетная симуляция (GameSim): spawn/kill/revive,
                  фиксированный шаг, столкновения, боты, строки снапшота,
                  custom-события
  arena.rs      — диск, выведенный из сетки карты, и `contains()`
  crystals.rs   — поле кристаллов: спавн, подбор, россыпь на смерти,
                  дельта-блок и его ресинк
  client/
    mod.rs      — GameClientDef: оверлей hot-буфера, блок игрока
    predictor.rs— реплика авторитетного движения + реконсиляция
```

`motion.rs` — файл, который делят обе половины. **Вынос логики из него
рассинхронизирует предсказание с сервером** — именно это ловит паритетный
набор тестов в `client/predictor.rs`.

## Сборка

```bash
npm run core:build        # обе цели
npm run core:build:web    # wasm-pack --target web    → core/pkg-web/
npm run core:build:node   # wasm-pack --target nodejs → core/pkg-node/
npm run core:test         # cargo test --workspace
```

`core/pkg-web/` грузит браузер (и напрямую импортирует `npm run dev`);
`core/pkg-node/` использует проект `integration` в `npm test` и headless-раннер
движка, а `npm run build` копирует его в `dist/core-node/`.

Crate зависит от `vimp-engine-core` с crates.io, версия закреплена в корневом
`Cargo.toml`. У `rapier2d` включён `enhanced-determinism`, а `indexmap` стоит
везде, где порядок вставки — контракт (модели, поля панели, змейки).

## ABI: команды, события, кадры

### Команды (`GameCore`)

`GameCoreAdapter` движка зовёт сгенерированную макросом поверхность:
`load_map`, `spawn_actor`, `remove_actor`, `reset_actor`, `reset_all_vitals`,
`spawn_scripted_actor`, `remove_scripted_actor`, `apply_input`, `apply_aim`,
`step`, `take_events`, `last_input_seq`, `is_alive`, `position_of`,
`players_data`, `alive_players`, `pack_body`, `pack_frame`, `frame_ptr` /
`frame_bytes`, `serialize_state` / `deserialize_state`, `debug_json`.

Что игра реализует за ними (`impl GameSim<SnakesGame> for SnakesSim`,
`core/src/game.rs`):

- **`spawn_actor` / `spawn_scripted_actor`** — создаёт `Snake` на свободном
  месте. Точка, предложенная движком, — только предложение:
  `find_spawn_from` обходит собственные точки респавна карты в порядке
  обращённых битов, а если не вышло — бросает `RESPAWN_ATTEMPTS` (24)
  случайных кандидата, держа `RESPAWN_CLEARANCE` (140) от каждого тела.
  Новая змейка выкладывается **целиком** (`Snake::lay_out_body`) и получает
  spawn-grace.
- **`apply_input`** — сопоставляет имя действия его биту через `KeyBits`
  (строится из `gameConfig.playerKeys`); клавиши `type: 1` (`respawn`)
  взводятся по `down` и потребляются ровно одним фиксированным шагом.
- **`apply_aim`** — цель указателя как мировая точка плюс флаги (удержание /
  ускорение двойным тапом). Становится `MoveInput.aim` и отменяется в момент,
  когда зажата клавиша поворота.
- **`is_alive` / `position_of` / `alive_players`** — читаются с головы ломаной.
- **`players_json`** (JSON за `players_data`) — все змейки, живые и мёртвые, в
  **порядке схемы**. Здесь встречаются два контракта: мёртвая змейка всё ещё
  участник (движку не сообщали о смерти), а этот payload — первый полный кадр
  для входящего клиента.
- **`reset_actor`** — движковый перезапуск раунда; он возрождает змейку вместо
  поштучного респавна, которого игра попросить не может.

### События (`take_events()`)

Стандартный словарь используется лишь частично. `PanelSet` и `PanelActive`
идут в HUD; **`Death` не эмитится никогда** (см.
[architecture.md](architecture.md#четыре-решения-на-которых-держится-код));
`Shake` не используется. Всё остальное едет как `CoreEvent::Custom`, который
движок дословно отдаёт в `HostPlugin.onCoreEvent`:

| `data.type` | Полезная нагрузка | Кто потребляет |
| --- | --- | --- |
| `crystals` | `{ id, total, gained }` | `StatBridge` — счёт, `eaten`, ранг за каждые 25 |
| `death` | `{ id, crystals, crashes, killer }` (`killer: null` — граница) | `StatBridge` — бонус за убийство, ранг убийце, сохранённый профиль |
| `respawn` | `{ id }` | сегодня никто; счётчики намеренно переживают жизнь |
| `population` | `{ count }` | `ArenaScaler` — пересборка карты; `StatBridge` — публикация строк новичков |

Id здесь **числа**, а в движке — **строки**; всё, что пересекает этот шов,
проходит через `String()`.

### Кадры

Упаковку кадра делает движок (формат v3, `SnapshotPacker`); игра поставляет
блоки, объявленные в `src/config/snapshot.js` и заполняемые в `game.rs`:

- **`s1`** (`indexed8`, класс `hot`) — строка на змейку: 16 точек хребта
  (32 float, голова первой), `angle`, `radius`, `crystals` (u16), `color` (u8),
  `boost` (u8). Последний байт несёт два бита: 0 — ускорение, 1 — spawn-grace
  (`boost_byte`).
- **`cr`** (`indexed32`, класс `event`) — поле кристаллов **дельтой**: строка
  при появлении, `null`-строка при поедании. Пересылается целиком при каждом
  спавне актёра, потому что вошедший клиент пропустил все прошлые строки.
- **`c1`** (`indexedNoNull8`, класс `hot`) — движковый блок динамики карты.
  Динамических тел в игре нет и блок остаётся пустым, но объявлен быть обязан:
  упаковщик отказывается от незнакомого ключа.

### Запросы состояния

`prediction_state` возвращает блок игрока —
`[x, y, cos, sin, crystals, length, alive, grace]`, `PLAYER_STATE_LEN = 8`.
Две несущие детали: курс едет как **cos/sin** (детектор дрейфа сравнивает
компоненты, и сырой угол на переходе через ±PI читается как расхождение 6.28
рад), а последний слот — **секунды оставшейся неуязвимости**, а не флаг: флаг
заморозил бы реплику на круг дольше, чем хост.

## Модель движения (`motion.rs`)

Ни ускорения, ни инерции. Один шаг — это:

```text
angle  = step_angle(head, angle, input, turn_speed_for(crystals), dt)
speed  = speed_of(input, can_boost, model)          // база или база * boostFactor
head   = advance_head(x, y, angle, speed, dt)
path.advance(head, model.point_spacing)             // оставить крошку
path.trim(length_for(crystals, model))              // подрезать хвост
```

- **`step_angle` — единственная функция поворота, и у неё два источника.**
  Клавиши просят «текущий угол ± шаг», указатель — «угол на эту точку». Оба
  ограничены `max_turn * dt`, поэтому мышь никогда не поворачивает быстрее
  `turnSpeed`. Цель ближе `AIM_DEAD_ZONE` (4 единицы) считается достигнутой,
  чтобы змейка не крутилась вокруг пальца.
- **`turn_speed_for`** — зеркало `radius_for`: та же кривая `sqrt(crystals)`,
  падающая вместо растущей, с полом `turnSpeedMin`.
- **`BodyPath`** — `VecDeque` крошек, голова первой. Рост означает, что с
  хвоста срезается *меньше*, поэтому тело всегда ровно той длины, которую
  диктует счётчик кристаллов — посегментного учёта нет нигде.
  `resample()` даёт фиксированный 16-точечный хребет для провода;
  `reset_with_body()` выкладывает целое тело прямо позади головы — благодаря
  чему змейка появляется целиком.

## Столкновения (`game.rs`, фиксированный шаг)

Шаг состоит из четырёх проходов, и их порядок и есть правило:

1. **Движение** каждой живой змейки (или сжигание её grace — змейка в grace не
   движется, не убивает, не может быть убита и не ест).
2. **Решение, кто кого убил** — со сбором в список, а не применением на месте:
   две змейки, въехавшие друг в друга на одном шаге, обязаны погибнуть обе, а
   разрешение по ходу дало бы выжить той, что итерируется первой.
   - голова против арены: `arena.contains(head, radius)` — граница ловит
     змейку, а не её осевую линию;
   - голова против каждого чужого тела: широкая фаза по AABB, затем
     `BodyPath::touches_ahead(head, radius_a + radius_b, facing)`. **Впереди**
     — это и есть правило вины: контакт обязан лежать в полуплоскости, куда
     смотрит голова, поэтому змейка, в которую врезались сбоку или сзади,
     выживает, а въехавшая — нет. Собственное тело пропускается целиком —
     голова проходит поверх своего хвоста.
3. **Подбор кристаллов** для тех, кто пережил этот шаг.
4. **Применение убийств**: `kill()` опустошает змейку, рассыпает `drop_ratio`
   груза по `DEATH_DROP_SPOTS` (24) точкам вдоль тела, которое она волокла
   (беря максимальный тир, который позволяет остаток бюджета, — чтобы крупная
   змейка оставляла кучу, за которой стоит ехать через арену), пишет две
   ячейки панели и эмитит `death`. Респавн — отдельный шаг по запросу игрока:
   `revive()` срабатывает, когда потреблён бит `respawn`.

## Поле кристаллов (`crystals.rs`)

Один `IndexMap<u32, Crystal>` плюс два дельта-аккумулятора, опустошаемых на
каждый упакованный кадр. Естественные спавны идут по таймеру
(`spawn_interval`), пока поле ниже `max_crystals`, в случайной точке диска за
вычетом `edge_margin`, с тиром, выпавшим по `tier_weights`. Подбор — проверка
расстояния до головы. `request_resync()` пересылает всё поле; `game.rs` зовёт
его при каждом спавне актёра.

## Боты

`drive_bot` (`game.rs`) намеренно мал: бот правит к ближайшему кристаллу и
отворачивает, когда то, что в `BOT_LOOKAHEAD` (220 единиц) перед ним, его
убьёт, — граница арены или чужое тело. Он пишет тот же `MoveInput`, что и
клавиши игрока, поэтому путь движения в игре ровно один. Боты — участники
движка (попадают в таблицу и занимают слот); JS-половина контракта —
`src/host/ScriptedManager.js`.

## ClientCore — клиентский режим ядра

`client/mod.rs` реализует `GameClientDef`:

- **`render_overlay`** — после того как движок проинтерполировал чужих змеек,
  строка локальной перезаписывается предсказанным хребтом, чтобы своя змейка
  не отставала от ввода. `crystals` и `color` читаются из авторитетной строки
  (`ROW_CRYSTALS`, `ROW_COLOR`), а не угадываются.
- **`predictor.rs`** — реплика. `apply_input`/`apply_aim` кладут ввод в
  историю; `update` интегрирует фиксированные шаги `timeStepMs`;
  `on_server_state` откатывается к авторитетному блоку игрока и переигрывает
  весь ввод новее него, а визуальная ошибка затухает за ~100 мс вместо рывка
  — если только она не превышает `ERROR_SNAP_DISTANCE` (100 единиц), что уже
  телепорт (респавн), а не дрейф, и применяется сразу.
- Grace отсчитывается и здесь, шаг в шаг, поэтому обе половины трогаются с
  места на одном тике.
- `set_model` (из `hooks.onAuth`) и `sync_panel` (из `hooks.onPanel`) —
  единственные написанные руками клиентские методы.

## Детерминизм

Флаг `--determinism` у headless-раннера переигрывает сценарий и сравнивает
хеши кадров; все пять сценариев обязаны проходить. Что это обеспечивает:
движковый `Rng` — единственный источник случайности (спавны кристаллов,
розыгрыш тира, броски респавна), `IndexMap` держит порядок итерации, `round2()`
квантует то, что уходит на провод, и внутри шага не читаются часы.

## Тесты

`cargo test --workspace` гоняет ~96 тестов, все внутри crate:

| Модуль | Что закрепляет |
| --- | --- |
| `motion.rs` | ограничение поворота, оба источника ввода, кривые роста, `BodyPath` (advance/trim/resample/touches/`touches_ahead`/`reset_with_body`) |
| `snake.rs` | семантика клавиш (зажатие против одноразовой), указатель, расход ускорения и его пол, респавн, grace, блок предсказания |
| `game.rs` | grace (замерла, безвредна, неуязвима), правило вины, появление целиком, размещение респавна (разнос, сначала точки карты, без самостолкновения), байт ускорения, ширина строки против схемы |
| `crystals.rs` | ритм и потолок спавна, подбор, россыпь на смерти, дельта и ресинк |
| `arena.rs` | диск из сетки, `contains` с радиусом |
| `client/predictor.rs` | **паритетный набор** — реплика и авторитетный шаг обязаны давать одинаковые позиции на одинаковом вводе, в том числе сквозь grace |

`tests/core/nodeCore.test.js` (Vitest, проект `integration`) гоняет настоящую
Node-сборку из JS: конфиг → `GameCore` → `step` → `pack_frame` → `ClientCore`
— шов, который Rust-тест не покрывает.
