### Что стоит знать про решения, отличающиеся от предложенных в разборе

- **П4.** Полный отказ ядра от собственной геометрии оказался слишком
  сильным: тестовая карта объявляет одну точку респауна, и восьми змеям
  расходиться было некуда. Итог — двухуровневый поиск: сперва точки карты
  (единственный источник геометрии), затем честно помеченный запасной обход
  диска, который ни на что в `arena.js` не ссылается и ничего про совпадение
  с ним не обещает. Если свободного места нет вовсе, возвращается самый
  просторный кандидат, а не запрошенная точка: стоять внутри чужого тела —
  гарантированная смерть в момент конца грейса.
- **П2.** Вместо резервирования мест под будущих людей в `ScriptedManager`
  выбрано правило движка, которое там уже есть: человек вытесняет бота
  (`removeOneForHuman`), как в `changeTeam`. Клампы `/bot` не тронуты.
- **П12.** «Публиковать при заведении записи» ничего бы не дало — запись
  заводится внутри первого же события, которое и так публикуется. Реальный
  хук — событие `population`, единственное, что приходит в бридж при

## Проблемы

### П1. `RoundManager.admitPlayer` выбирает точку спавна по размеру команды — индексы коллизятся (движок, высокая)

`packages/engine/src/host/meta/core/RoundManager.js:307-317`:

```js
const respawns = this._scaledMapData?.respawns?.[user.team];
const index = this._participants.getTeamSize(user.team) - 1;
```

`getTeamSize()` — это счётчик состава команды, а не аллокатор слотов. Он
совпадает с «индексом новичка» только если участники добавляются и
обслуживаются строго по одному и никогда не выходят. Ни одно из этих условий не
выполняется:

1. **Одновременный вход.** `createHuman` (и `addToTeam`) происходит в
   `createUser`, а `admitPlayer` — сильно позже, в `firstShotReady`, после
   загрузки карты клиентом. Двое зашедших почти одновременно дают:
   `createHuman(A)` → size 1, `createHuman(B)` → size 2, `firstShotReady(A)` →
   index 1, `firstShotReady(B)` → index 1. **Оба на одной точке.**
2. **Выход и повторный вход.** Игрок с индексом 1 из трёх вышел → size 2 →
   следующий зашедший получает index 2, уже занятый.
3. **Смена карты — 100 % коллизия.** В `createMap` (строки 138–184) сначала
   `resetTeamSizes()`, потом цикл по всем людям с `addToTeam(...)`, и только
   потом клиенты по одному доходят до `firstShotReady`. К этому моменту
   `getTeamSize()` уже равен N для всех, поэтому **все игроки получают один и
   тот же индекс N−1**.

В `vimp-snakes` это не видно только потому, что этап 3 положил в ядро
`find_spawn_from` — он и переносит дубликаты. То есть движковый метод сейчас
корректен ровно в той игре, которая сама чинит его результат; любая другая игра,
включившая `noSpectators`, получит стопку змей/танков на одной точке (в танках —
мгновенный телефраг или застревание в геометрии).

**Решение.** Выдавать первый *свободный* индекс, а не «размер минус один».
Занятость определяется по активным участникам команды, у которых уже есть актор:

```js
// RoundManager.js
// Индекс точки спавна — первый не занятый активным участником команды.
// Размер команды для этого не годится: он меняется на входах и выходах,
// а между добавлением в команду (createUser) и выдачей актора
// (firstShotReady) проходит вся загрузка карты клиентом.
_freeRespawnIndex(team) {
  const respawns = this._scaledMapData?.respawns?.[team] ?? [];
  const taken = new Set();

  for (const gameId of this._participants.getActiveList()) {
    const user = this._participants.get(gameId);

    if (user?.team === team && Number.isInteger(user.respawnIndex)) {
      taken.add(user.respawnIndex);
    }
  }

  for (let i = 0; i < respawns.length; i += 1) {
    if (!taken.has(i)) {
      return i;
    }
  }

  return -1;
}

admitPlayer(gameId) {
  const user = this._participants.get(gameId);

  if (!user || user.team === this._spectatorTeam) {
    return false;
  }

  const index = this._freeRespawnIndex(user.team);
  const respawnData = this._scaledMapData?.respawns?.[user.team]?.[index];

  if (!respawnData) {
    this._chat.pushSystemByUser(gameId, 'TEAMS_TEAM_FULL', [
      user.team,
      user.team,
    ]);

    return false;
  }

  user.respawnIndex = index;
  this._setActivePlayer(user, respawnData);

  return true;
}
```

`user.respawnIndex` заводится в `Participant` (значение по умолчанию `null`) и
сбрасывается в `_setSpectatorFromActivePlayer` и в `removeActive`. Тем же
приёмом стоит починить и `changeTeam` (строка 418) — там ровно та же формула и
та же болезнь, просто она старше этой задачи.

**Тесты, которых не хватает:** два подряд `admitPlayer` в команде с двумя
точками должны дать точки 0 и 1; после выхода первого третий получает 0;
`createMap` + два `admitPlayer` не дают одинаковых точек.

### П2. Отказ `admitPlayer` — тупик без обратной связи (движок, высокая)

`admitPlayer` возвращает `false` молча: ни системного сообщения, ни повторной
попытки. Под `noSpectators` у игрока при этом **нет способа попросить место** —
голосования нет, `changeTeam` в единственную команду отвечает «это ваша текущая
команда». Человек висит без актора: жив в stat-таблице, ни во что не играет и не
понимает почему.

Достижимо это двумя путями: точки кончились (сейчас граница ровно сходится —
64 точки против `maxPlayers: 32` + `/bot`, клампленного тем же числом; поднимите
`maxPlayers` в форме комнаты, и она перестанет сходиться) либо
`_scaledMapData` ещё не готов.

**Решение.** Три части, все дешёвые:

1. Системное сообщение при отказе (код `TEAMS_TEAM_FULL` уже есть) — см.
   патч в П1.
2. Явно задокументировать путь восстановления: `_startRound` выдаёт актора
   всем, у кого `team !== spectatorTeam` и `isReady`, поэтому `/bot N` и `/nr`
   лечат зависшего игрока. Строка в `docs/ai/03-host-plugin.md` рядом с
   описанием `noSpectators`.
3. На стороне игры — клампить `/bot` не по `maxPlayers`, а по остатку:
   `Math.min(wanted, respawns.length - humansInTeam)` в
   `src/host/ScriptedManager.js:_hasRoom` (там уже есть `getTeamSize`, надо лишь
   зарезервировать места под людей, которых комната ещё может впустить).

### П3. Детерминированный обход спавна покрывает только 24 из 64 точек (ядро, средняя)

`core/src/game.rs:279` — `for attempt in 0..RESPAWN_ATTEMPTS` при
`RESPAWN_ATTEMPTS = 24` и `SPAWN_SLOTS = 64`. Константа взята у случайного
поиска, где 24 броска — разумный бюджет, но у детерминированного обхода смысл
другой: он обязан перебрать **все** слоты, иначе на людной арене (32 бота + люди)
возвращается `requested` — та самая занятая точка. Две змеи оказываются друг в
друге, и в момент истечения грейса обе умирают одновременно. Это ровно тот
сценарий, ради которого этап 3 и делался.

Цена полного обхода ничтожна: 64 кандидата × ~40 змей × `touches` — один раз на
спавн, вне горячего цикла.

**Решение.**

```rust
/// Сколько кандидатов перебирает детерминированный обход. Не
/// `RESPAWN_ATTEMPTS`: у случайного поиска это бюджет бросков, здесь — весь
/// список слотов, и обрывать его на трети значит возвращать занятую точку
/// при живой свободной.
const SPAWN_WALK_ATTEMPTS: u32 = SPAWN_SLOTS;

for attempt in 0..SPAWN_WALK_ATTEMPTS {
    ...
}
```

Плюс тест: занять 40 слотов и убедиться, что 41-я змея всё равно встаёт на
свободное место, а не на `requested`.

Отдельно стоит подумать о «наименее плохом» финале вместо `requested`: если
свободного нет вообще, вернуть кандидата с максимальным расстоянием до
ближайшего тела — умирать сразу после грейса всё же хуже, чем стартовать тесно.

### П4. Подсолнух продублирован в JS и Rust — и формулы не совпадают (ядро/данные, средняя)

Док-комментарий `find_spawn_from` утверждает: «The candidates are the sunflower
spiral of `src/data/maps/arena.js`… so the two agree on what a well-spread arena
looks like». Они не совпадают:

| | `src/data/maps/arena.js` | `core/src/game.rs` |
| --- | --- | --- |
| радиус | `radius * RESPAWN_SPAN * sqrt(...)` | `(radius - edge_margin) * RESPAWN_SPAN * sqrt(...)` |
| координаты | округляются до целых | `f32` |
| угол | `GOLDEN_ANGLE` из `Math.PI * (3 - sqrt 5)` | литерал `2.399_963_2` |

Для базового размера это сдвиг кандидатов внутрь примерно на 5 % — не баг, но
инвариант «зазор ≥ 140/178», посчитанный на JS-точках, к Rust-точкам формально
не относится, а комментарий обещает обратное. Плюс продублированы `reverse_bits`,
`RESPAWN_SPAN` и золотой угол — три константы, которые обязаны меняться вместе и
ничем не связаны.

**Решение (предпочтительное).** Ядру не нужен собственный подсолнух: точки
респауна приходят в `ctx.map.respawns` и уже собираются в `on_fixed_step`
(`map_points`). Достаточно закэшировать их при смене карты и обходить в
бит-реверсном порядке этот список:

```rust
// поле SnakesSim
spawn_slots: Vec<[f32; 3]>,   // точки респауна карты, как их прислал движок

// в on_fixed_step, там же где строится map_points
if self.spawn_slots != map_points {
    self.spawn_slots = map_points.clone();
}

fn find_spawn_from(&self, seed: u32, requested: [f32; 3]) -> [f32; 3] {
    let n = self.spawn_slots.len();

    if n == 0 || self.arena.radius <= 0.0 || self.is_clear([requested[0], requested[1]]) {
        return requested;
    }

    let bits = usize::BITS - (n - 1).leading_zeros(); // n не обязан быть степенью двойки
    for attempt in 0..n {
        let k = reverse_bits_n((seed as usize + attempt) % n, bits);
        if k >= n { continue; }
        let slot = self.spawn_slots[k];
        if self.is_clear([slot[0], slot[1]]) {
            return self.facing_centre([slot[0], slot[1]]);
        }
    }

    requested
}
```

Это убирает дублирование целиком: точки ядра становятся ровно точками карты,
`RESPAWN_SPAN`/`GOLDEN_ANGLE`/`SPAWN_SLOTS` из `game.rs` исчезают, а согласие
двух половин перестаёт быть обещанием в комментарии.

**Решение (минимальное), если переделывать не хочется:** привести формулу
радиуса к JS-варианту (`self.arena.radius * RESPAWN_SPAN`), заменить литерал
угла на `std::f32::consts::PI * (3.0 - 5.0f32.sqrt())` и добавить тест паритета
«первые 8 кандидатов ядра совпадают с первыми 8 точками `arena.json` в пределах
1 единицы».

### П5. `reset_actor` ищет место, натыкаясь на собственное тело (ядро, средняя)

`core/src/game.rs:604` — `find_spawn_from` вызывается до `snake.respawn(...)`,
то есть змея ещё жива и её тело лежит в `self.snakes`. `is_clear` перебирает
**все** живые тела, включая её собственное. Следствия: точка, свободная от
чужих, объявляется занятой; у длинной змеи её собственное тело способно
заблокировать заметную часть кандидатов.

**Решение.** Параметризовать исключение:

```rust
fn is_clear_except(&self, point: [f32; 2], skip: Option<u32>) -> bool {
    self.snakes.iter().all(|(id, other)| {
        Some(*id) == skip || !other.alive || !other.path.touches(point, RESPAWN_CLEARANCE, 0)
    })
}

fn is_clear(&self, point: [f32; 2]) -> bool {
    self.is_clear_except(point, None)
}
```

и в `find_spawn_from` принимать `skip: Option<u32>`, передавая `Some(game_id)`
из `reset_actor` и `None` из `spawn_actor`. Тест: змея с длинным телом,
респавнящаяся на свободном от чужих месте, не переносится.

### П6. Бит-реверс молча ломается на не-степени двойки (данные/ядро, средняя)

`src/data/maps/arena.js:100`:

```js
const RESPAWN_BITS = Math.round(Math.log2(RESPAWN_COUNT));
```

При `RESPAWN_COUNT = 48` это даст `RESPAWN_BITS = 6`, `reverseBits` вернёт
индексы вплоть до 63 → `sqrt((k + 0.5) / 48)` больше единицы, часть точек уедет
за `RESPAWN_SPAN`, а часть индексов будет выдана дважды: **дублирующиеся точки
респауна без единой ошибки**. В `game.rs` та же ловушка разбита на две
независимые константы (`SPAWN_SLOTS = 64` и `SPAWN_SLOT_BITS = 6`), которые
никто не связывает.

**Решение.** Отказ должен быть громким:

```js
// arena.js
if (!Number.isInteger(Math.log2(RESPAWN_COUNT))) {
  throw new Error(
    `RESPAWN_COUNT must be a power of two (bit-reversed order), got ${RESPAWN_COUNT}`,
  );
}
```

и в `core/src/game.rs`:

```rust
const SPAWN_SLOT_BITS: u32 = SPAWN_SLOTS.trailing_zeros();
const _: () = assert!(SPAWN_SLOTS.is_power_of_two());
```

Плюс тест в `tests/config/contract.test.js`: 64 точки респауна попарно
различны (сейчас проверяется только префиксное покрытие и зазор).

### П7. README игры описывает старую модель очков (документация, средняя)

`README.md:31-40` — прямое противоречие этапам 4 и 6:

> Three numbers follow you… **eaten**, **kills** and **score**, which is the
> crystals you ate plus **the entire score of everyone you killed**. Killing the
> leader is worth the double: **you take their whole score**… The HUD shows all
> three… The stat table (`Tab`) is a single leaderboard ranked by score, **ties
> broken by crystals eaten**.

Фактически: `score = eaten + 15 * kills`, HUD показывает только `score`, таблица
— `snake / status / rank / score / ping`, тай-брейк по `rank`. Кроме того, в
README нет ни грейса, ни падения манёвренности — а это две механики, которые
игрок видит первыми.

### П10. Грейс приезжает предиктору булевым, а не остатком (ядро/клиент, низкая)

Слот 7 несёт `in_grace() as f32`, то есть 0/1. Предиктор замирает, пока флаг
взведён, и узнаёт об окончании грейса только из следующего серверного кадра.
Итог: на конце грейса своя змея стоит лишних ~RTT, а затем догоняет авторитет
рывком (в пределах `ERROR_SNAP_DISTANCE`, так что визуально это лерп, но
управление на четверть секунды «залипает»).

**Решение,** если это заметно на игре: класть в слот 7 остаток в секундах,
предиктор знает `step_ms` и умеет сам его дожигать:

```rust
// snake.rs
self.spawn_grace,                     // вместо self.in_grace() as u8 as f32

// predictor.rs
if self.state.grace > 0.0 {
    self.state.grace = (self.state.grace - dt).max(0.0);
    return;
}
```

Совместимость: `SnakeState.grace` становится `f32`, порог `> 0.5` в
`from_slice` уходит, `thresholds` сценариев на слот 7 не смотрят. Байт `boost`
на проводе не меняется — он и должен оставаться булевым для отрисовки.

### П11. `ArenaScaler.reapply()`: комментарий неточен, и змеи после `/bot` живут в под-диске (игра, низкая)

1. Комментарий утверждает: «the engine's round restart re-sent them the base map
   too». Движок при `initiateNewRound` карту клиентам **не рассылает** —
   `_startRound` трогает только ядро (`_game.createMap`) и шлёт `sendClear`.
   Сброс `_delivered` всё равно нужен (клиент, вошедший между ресайзами, держит
   каталожную карту), но обоснование стоит написать верное.
2. Порядок в `botCommand`: `initiateNewRound()` расставляет всех по точкам
   **базовой** карты (движок держит `_scaledMapData` каталога), и только потом
   `reapply()` возвращает ядру увеличенный диск. Змеи остаются в центральном
   под-диске увеличенной арены — при `/bot 20` это заметный сдвиг всей компании
   в один угол. Не смертельно (все внутри границы, зазор 178 сохраняется), но
   это половина той же проблемы, что этап 3 чинил.

**Решение.** Чисто игровым кодом это не закрывается: `_scaledMapData` —
приватное поле движка. Правильный ход — движковый хук, симметричный тому, что
уже есть у карты:

```js
// RoundManager.js
// Подменяет карту, которую движок раздаёт при старте раунда, не трогая
// текущую карту комнаты и не начиная новый раунд: для игр, которые сами
// пересобирают геометрию на лету (vimp-snakes/ArenaScaler).
overrideMapData(mapData) {
  this._scaledMapData = mapData;
}
```

плюс проброс через `HostGame.overrideMapData(mapData)`. Тогда `ArenaScaler`
вызывает его в `_apply()` вместе с `coreAdapter.createMap`, и любой
`initiateNewRound` (`/bot`, `/nr`) расставляет всех уже по актуальному диску —
`reapply()` после `/bot` становится не нужен вовсе.

### П12. Ранг появляется в таблице только после первого события (игра, низкая)

`_publish` вызывается лишь из `_onCrystals`/`_onDeath`. Вошедший игрок с рангом
120 висит с `rank = 0` (значение `bodyValue`) до первого съеденного кристалла.
Само-лечится быстро, но первые секунды таблица врёт.

**Решение:** публиковать запись сразу при её заведении — в `_record()`, когда
запись создаётся, вызвать `_publish(gameId, record, vimp, panel)`. Ранг к этому
моменту может быть ещё не загружен с мастера (`PlayerDataSync.load` асинхронен),
поэтому `undefined` по-прежнему не пишется, а первое событие докрутит.

### П13. Дыры в тестах

Не покрыто (в порядке важности):

1. два `admitPlayer` подряд → разные точки (П1); `createMap` + `admitPlayer` для

команды, а не её размера.
