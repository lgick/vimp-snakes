## R1. `.vimp-shell > canvas` ломает раскладку оверлейных полотен других игр (движок, ВЫСОКАЯ) — ИСПРАВЛЕНО (✅ выполнен в коде, визуальная проверка радара танков за пользователем)

**Подтверждено пользователем на `vimp-tanks`: радар уехал из угла.**

### Механика

Правило этапа 8 целилось в тип элемента:

```css
.vimp-shell > canvas {
  position: absolute;
  top: 0; bottom: 0; left: 0; right: 0;
  margin: auto;
}
```

`ensureCanvas` кладёт в контейнер ВСЕ полотна из
`modules.canvasManager.canvases`, а не одно игровое. У танков их два:

```js
vimp:  { width: 960, height: 600, aspectRatio: '16:9', baseScale: '5:1' },
radar: { width: 150, height: 150, fixSize: '150',      baseScale: '1:8' },
```

`src/client/tanks.css` кладёт радар в правый верхний угол:

```css
#radar { position: absolute; right: 1%; top: 35px; z-index: 2; }
```

Специфичность здесь ни при чём — `#radar` (0,1,0,0) выигрывает у
`.vimp-shell > canvas` (0,0,1,1) по тем свойствам, которые объявляет.
Проблема в НЕобъявленных: `bottom`, `left` и `margin` в игровом правиле
отсутствуют и приезжают из движкового. Итог — `top: 35px; bottom: 0;
left: 0; right: 1%; margin: auto`: элемент известного размера при заданных
обеих парах смещений и `margin: auto` центрируется в получившейся коробке.
Радар оказывается посреди экрана.

`#vimp` у танков не пострадал: он объявляет весь набор
(`top/bottom/left/right/margin`) сам.

Это ровно тот класс регрессии, который просили не допустить: движковое
правило по типу элемента вторгается в раскладку, которую игра держит сама.

### Решение (применено)

Правило ограничено классом, который движок вешает только на то полотно,
размер которого он же и считает.

- `packages/engine/src/client/views/gameShell.js` — экспорт
  `LETTERBOX_CLASS = 'vimp-letterbox'`; `ensureCanvas` добавляет его при
  создании полотна, если в конфиге канваса **нет `fixSize`**.
- `packages/engine/src/client/style.css` — селектор стал
  `.vimp-shell > canvas.vimp-letterbox`, комментарий объясняет, почему
  селектора по типу мало.
- `tests/client/gameShell.test.js` — два кейса: полотно с `aspectRatio`
  помечается, полотно с `fixSize` — нет.
- `docs/en/client.md`, `docs/ru/client.md`, `docs/_ru/client.md`,
  `packages/engine/CHANGELOG.md` (`### Fixed`).

Почему дискриминатор именно `fixSize`, а не новый ключ конфига: это уже
существующая развилка `CanvasManagerModel.resize` — ветка `fixSize` отдаёт
полотну размер из конфига и не считает `currentScale`, то есть такое полотно
по определению оверлей игры, а не леттербокс движка. Новый ключ пришлось бы
объявлять в каждой игре, а `fixSize` уже объявлен там, где надо.

**Влияние на игры.** Танки: `#vimp` получает класс, но его собственное
правило объявляет все те же свойства — раскладка байт в байт прежняя; `#radar`
класса не получает и возвращается в угол. Snakes: единственное полотно —
`vimp` с `aspectRatio` и без `fixSize`, центрирование сохраняется. Полотно,
которое игра разместила в своей разметке сама, `ensureCanvas` как не переносил,
так и не помечает — теперь это правда, а не оговорка в документации.

**Не проверено вживую в браузере** (нужен `npm run dev` танков с ядром);
проверка — визуальная, на 30 секунд, и её стоит сделать перед коммитом.

## R2. Бит-реверсный обход слотов пропускает точки карты, если их число не степень двойки (ядро, средняя) — ✅ выполнен

`core/src/game.rs`, `find_spawn_from`:

```rust
let bits = usize::BITS - (slots - 1).leading_zeros();

for attempt in 0..slots {
    let k = reverse_bits((seed + attempt) % slots, bits);

    // the bit-reversal of a range that is not a power of two overshoots
    // it; those indices are simply not candidates
    let Some(slot) = self.spawn_slots.get(k) else {
        continue;
    };
```

Док-коммент над функцией обещает: «EVERY slot is tried before giving up».
Это неверно. `reverse_bits(_, bits)` — биекция на `[0, 2^bits)`, а не на
`[0, slots)`. Цикл делает ровно `slots` попыток по входам `0..slots`, часть
образов вылетает за `slots` и отбрасывается — и на их место ничего не
подставляется. Пропущенные индексы недостижимы **при любом `seed`**: сдвиг
seed'ом только вращает множество входов, а множество входов одно и то же
`{0..slots-1}`.

Для `slots = 5` (`bits = 3`): 0→0, 1→4, 2→2, 3→6 (за границей), 4→1.
Индекс **3 не проверяется никогда**.

Проверено экспериментально (временный тест, в дерево не попал): карта с пятью
точками, четыре заняты, свободна ровно точка 3 —

```
landed at [1284.04, 450.81]; free map slot 3 is [1280.0, 680.0]; on it: false
```

Змея ушла в запасной обход диска вместо свободной точки карты, объявленной
самой картой.

**Почему это не рвётся сегодня:** `arena.js` объявляет ровно 64 точки и с
этого коммита бросает на не-степени двойки. То есть инвариант держится
СОСЕДНИМ файлом, а комментарий в ядре обещает то, чего код не делает. Любая
другая карта (ручная, из каталога мастера, тестовая фикстура) молча теряет
часть точек.

**Решение.** Крутить счётчик по полному диапазону перестановки, а не по числу
слотов — тогда каждый индекс `< slots` встречается ровно один раз:

```rust
let span = 1usize << bits;              // >= slots, степень двойки
let mut tried = 0;

for attempt in 0..span {
    let k = reverse_bits((seed + attempt) % span, bits);

    let Some(slot) = self.spawn_slots.get(k) else {
        continue;                        // образ вне списка — не кандидат
    };

    tried += 1;
    ...
}

debug_assert_eq!(tried, slots, "the walk must visit every slot exactly once");
```

Цена — не больше `2 * slots` итераций, всё так же вне горячего цикла.
Альтернатива, если хочется оставить обещание строгим: потребовать степень
двойки и в ядре (`debug_assert!(slots.is_power_of_two())`), но это перекладывает
на карту требование, которого движковый контракт `respawns` не содержит.

Заодно поправить док-коммент: сейчас он утверждает больше, чем делает код.

## R3. `getPlayerRank` никогда не возвращает `undefined`, и П12 чинит только колонку score (игра + движок, средняя) — ✅ выполнен

Две сцепленные ошибки.

**1. Защита в `_publish` не работает.** `src/host/StatBridge.js`:

```js
const rank = vimp?.getPlayerRank?.(gameId);

if (rank !== undefined && rank !== null) {
  columns.rank = rank;
}
```

Комментарий над методом: «A missing method or a missing player gives
`undefined`, and that is NOT written». Про метод — правда, про игрока — нет:

```js
// PlayerDataSync.js
getRank(participantId) {
  return this._entries.get(participantId)?.rank ?? 0;
}
```

Для незнакомого id возвращается **0**, а не `undefined`. Колонка объявлена
`bodyMethod: '='`, то есть ноль затирает известный ранг — ровно то, что
комментарий обещает предотвратить.

**2. Ранг новичка всё ещё показывается нулём.** `PlayerDataSync.load()`
кладёт запись с `rank: 0` синхронно и уходит на `await` за настоящим
значением. Событие `population` приходит из ядра при появлении актора; к этому
моменту `getRank` уже отвечает `0` — не `undefined`. Значит
`_publishNewcomers` пишет `rank = 0`, ставит `record.published = true`, и
больше событие `population` эту строку не трогает. Настоящий ранг (например,
120) появится только с первым съеденным кристаллом — то есть ровно тот эффект,
против которого делался П12, просто теперь он спрятан за записанным нулём.

В `PlayerDataSync` уже есть поле, которое отвечает на нужный вопрос:
`entry.rankLoaded` (заведено в кодревью F4 именно для того, чтобы не PUT'ить
дефолт поверх настоящего значения).

**Решение (два шага, оба маленькие).**

Движок — открыть загруженность наружу:

```js
// PlayerDataSync.js
isRankLoaded(participantId) {
  return this._entries.get(participantId)?.rankLoaded === true;
}

// HostGame.js — рядом с getPlayerRank
// загружен ли ранг с мастера. Сам getPlayerRank отвечает 0 и для незнакомого
// id, и до ответа auth — игре, которая пишет ранг в stat колонкой '=',
// нужно отличать «ранг 0» от «ранга ещё нет»
isPlayerRankLoaded(gameId) {
  return this._playerDataSync.isRankLoaded(gameId);
}
```

Игра — писать ранг только когда он настоящий, и не считать строку
опубликованной, пока ранга нет:

```js
_publish(gameId, record, vimp, panel) {
  const { score } = record;
  const columns = { score };
  const rankReady = vimp?.isPlayerRankLoaded?.(gameId) ?? false;

  if (rankReady) {
    columns.rank = vimp.getPlayerRank(gameId);
  }

  // строка считается выданной, только когда в ней есть всё, что событие
  // 'population' обязано было показать: пока ранг не приехал, следующий
  // join/leave попробует ещё раз
  record.published = rankReady;
  ...
}
```

Тесты: ранг не пишется, пока `isPlayerRankLoaded` ложь; после загрузки
следующее `population` дописывает строку; движок без нового метода
(`?? false`) не роняет бридж, а просто не пишет колонку.

Если трогать движок не хочется — минимум — снять `published` при отсутствии
ранга и republish'ить на каждом `population`: событий этих ровно столько,
сколько входов и выходов.

## R4. `ArenaScaler.reapply()` после `overrideMapData` стал дорогим no-op (игра, средняя) — ✅ выполнен

П11 сделан правильно: `_apply()` теперь держит движковую копию карты в
актуальном состоянии, и `_startRound` (`this._game.createMap(this._scaledMapData)`)
перезагружает ядро уже правильной геометрией. Из этого следует, что
`reapply()` после `initiateNewRound()` больше ничего не чинит — комментарий
это признаёт («дешевле переслать карту, чем рассуждать, кто что перезагрузил»),
но пересылка не бесплатна:

```js
this._delivered.clear();
this._broadcast();
```

`_delivered.clear()` заставляет `_broadcast` отправить `MAP_DATA` **всей
комнате** на каждый `/bot`. По собственному комментарию класса, MAP_DATA на
клиенте «destroys the parts of this setId, rebuilds them from the payload and
re-runs `clientCore.set_map`» — то есть каждая `/bot N` пересобирает арену у
всех, кто в комнате, без единой причины: `_startRound` карту клиентам не
рассылает (он шлёт только `sendClear` и дефолтные keyset'ы), значит их копия
и так актуальна.

Аргумент «клиент, вошедший между ресайзами, держит каталожную карту» тоже не
про `reapply`: такого клиента ловит обычный `_broadcast()` — у него в
`_delivered` вообще нет записи. А `/bot`, создающая ботов, меняет население и
сама приводит к `_apply` → `_broadcast`.

**Решение.** Самое честное — убрать `reapply()` и его вызов из
`botCommand.js` (и два теста на него), оставив `_apply`. Если хочется страховки
на случай, что движок когда-нибудь начнёт перезагружать карту иначе, —
оставить метод, но не трогать `_delivered`:

```js
reapply() {
  if (!this._mapData) {
    return;
  }

  this._vimp?.overrideMapData?.(this._mapData);
  this._coreAdapter.createMap(this._mapData);
  this._scriptedManager?.createMap(this._mapData);

  // без _delivered.clear(): клиенты карту от старта раунда не получают,
  // их копия и так текущая, а лишний MAP_DATA пересобирает у них части
  this._broadcast();
}
```

Тест `reapply` при этом переписывается на «клиентам ничего не ушло, ядру и
боту — ушло».

## R5. `changeTeam` обнуляет слот до проверки и может оставить активного игрока без него (движок, низкая) — ✅ выполнен

`RoundManager.changeTeam`:

```js
user.respawnIndex = null;

const respawnIndex = this._freeRespawnIndex(newTeam);
const respawnData = respawns[newTeam][respawnIndex];

if (!respawnData) {
  this._chat.pushSystemByUser(gameId, 'TEAMS_TEAM_FULL', [newTeam, currentTeam]);
  return;
}
```

Ранний `return` уходит уже после `removeFromTeam`/`addToTeam`,
`user.team = newTeam`, `stat.moveUser` — участник числится в новой команде,
актор у него старый, а `respawnIndex` теперь `null`. Его физически занятая
точка выглядит свободной для следующего `_freeRespawnIndex`.

Достижимость низкая: выше по методу стоит гейт
`respawns[newTeam].length <= getTeamSize(newTeam)` (с вытеснением бота),
после которого свободный индекс существует всегда. То есть это не активный
баг, а ловушка на будущее: гейт и аллокатор считают занятость по-разному
(размер команды против записанных слотов), и стоит им разойтись — состояние
станет несогласованным молча.

**Решение.** Считать индекс до мутаций и обнулять слот только на успешном
пути:

```js
const respawnIndex = this._freeRespawnIndex(newTeam, gameId); // gameId исключить
const respawnData = respawns[newTeam][respawnIndex];

if (!respawnData) {
  this._chat.pushSystemByUser(...);
  return;   // user.respawnIndex не тронут
}

user.respawnIndex = respawnIndex;
```

где `_freeRespawnIndex(team, exceptGameId)` пропускает самого переходящего —
это заодно снимает необходимость временного `null`.

## R6. `admitPlayer` вытесняет бота, когда точек нет вовсе (движок, низкая) — ✅ выполнен

```js
let index = this._freeRespawnIndex(user.team);

if (!respawns?.[index] && this._scripted.removeOneForHuman?.(user.team)) {
  index = this._freeRespawnIndex(user.team);
}
```

Условие не различает «слоты кончились» и «карты ещё нет»: при
`_scaledMapData === undefined` (или `respawns[team]` пустом) `respawns?.[index]`
тоже `undefined`, и бот удаляется впустую — место от этого не появится, а
игрок всё равно получит отказ. Практически недостижимо (`admitPlayer` живёт в
`firstShotReady`, карта к этому моменту есть), но правило «человек вытесняет
бота» должно срабатывать только там, где вытеснение помогает.

**Решение:**

```js
const hasSlots = Boolean(respawns?.length);

if (hasSlots && index === -1 && this._scripted.removeOneForHuman?.(user.team)) {
  index = this._freeRespawnIndex(user.team);
}
```

## R7. `TEAMS_TEAM_FULL` под `noSpectators` сообщает игроку неправду (движок + игра, низкая) — ✅ выполнен

Текст кода — `Team {0} is full. Your current team: {1}`
(`systemMessages.js`, группа `s`, индекс 0), и `admitPlayer` подставляет в оба
слота одну и ту же команду:

```js
this._chat.pushSystemByUser(gameId, 'TEAMS_TEAM_FULL', [user.team, user.team]);
```

Игрок читает «Team players is full. Your current team: players» — вторая
половина сообщает, что всё в порядке и он в игре, тогда как актора у него как
раз нет. Диагностическая ценность отрицательная.

**Решение.** Отдельный код (`TEAMS_NO_SLOT`) с текстом вида «Мест на карте
нет: вы вступите в игру со следующим раундом». Цена — новая строка в конце
группы `s` у КАЖДОЙ игры (индекс внутри группы и есть код, дописывать можно
только в хвост: `src/config/client.js` в snakes прямо об этом предупреждает,
у танков придётся дописать такую же). Дешёвая альтернатива, если плодить код
не хочется, — передать вторым аргументом статус, а не команду, и переписать
движковый текст на нейтральный.

## R8. Тест на толпу проверяет в 168 раз меньше, чем держит код (игра, низкая) — ✅ выполнен

`a_crowd_past_the_map_points_still_gets_room_instead_of_a_heap` заявляет в
комментарии «Nobody may be left standing inside somebody else», а проверяет:

```rust
if (a[0] - b[0]).hypot(a[1] - b[1]) < 1.0 {
    stacked += 1;
}
```

Одна единица мира при `RESPAWN_CLEARANCE = 140` — это «внутри друг друга»
буквально. Замерил фактическое поведение на той же фикстуре (40 змей, одна
точка на карте):

```
min gap 168.09879, pairs under clearance: 0
```

То есть код держит настоящий зазор, а тест разрешает кучу. Такой тест не
поймает регрессию запасного обхода — ради которой и написан.

**Решение:** сравнивать с `RESPAWN_CLEARANCE` (сейчас проходит с запасом),
а если запас захочется оставить на будущие изменения раскладки — с явной
долей от него и комментарием, откуда взято число.

## R9. Мелочи в `StatBridge.js` (игра, низкая) — ✅ выполнен

## R10. Соседний неверный комментарий (игра, низкая, не из этой задачи) — ✅ выполнен

`src/host/ScriptedManager.js`, `removeScripted`:

> The copy is not a style choice. `getScripted()` hands back the registry's
> LIVE array, and `_remove` splices out of that same array…

`ParticipantManager.getScripted()` — это `getAll().filter(...)`, а
`getAll()` — `[...this._participants.values()]`. Оба возвращают новый массив,
живого массива реестра наружу не выдаётся, а `remove()` работает с `Map`, а не
со `splice`. Копия безвредна, но обоснование под ней описывает механику,
которой в коде нет, — и следующий читатель будет искать её в реестре. Либо
убрать копию, либо переписать комментарий на «копия на случай, если реестр
когда-нибудь начнёт отдавать своё хранилище».

## R11. `spawn_slots` и арена живут одним фикс-шагом (ядро, информационно) — ✅ выполнен

`spawn_slots` обновляется только в `on_fixed_step`, как и `Arena`. Значит в
окне между `coreAdapter.createMap` (горячая подмена от `ArenaScaler`) и
ближайшим шагом `spawn_actor` ищет место по СТАРЫМ точкам в СТАРОМ диске.
Дефекта тут нет — обе величины устаревают синхронно, и точка старой карты
лежит внутри старого радиуса, — но это неочевидно и стоит одной строки в
док-комментарии `spawn_slots`: «обновляется в паре с `Arena`, поэтому
кандидаты и границы всегда из одной и той же карты».
