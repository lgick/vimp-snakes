# Этап 2: panel, stat и система очков

Пункты пользователя 5, 7, 2. Правки только в `vimp-snakes`. Этап большой,
поэтому разбит на подшаги: сначала общая для обеих таблиц схема очков,
затем панель, затем stat, затем окно результата.

## Схема очков — общая для panel, stat и game over

Сегодня в игре ровно одна величина: `crystals` — сколько змейка **несёт
прямо сейчас**. Смерть её обнуляет. Пользователю нужны три разные величины,
и путать их нельзя:

| Величина | Смысл | Обнуляется смертью |
| --- | --- | --- |
| `eaten` | сколько кристаллов съедено за игру, накопительно | нет |
| `kills` | сколько противников врезалось в эту змейку | нет |
| `score` | общие очки: `eaten` + сумма счетов убитых | нет |
| `crystals` | несёт сейчас — нужно геймплею (длина, буст, россыпь) | да |

**Очки за убийство: весь счёт жертвы целиком** (решение пользователя).
В момент убийства `killerScore += victimScore`, где `victimScore` — значение
`score` жертвы на этот момент, до его обнуления (обнуления `score` при
смерти как раз и не происходит — обнуляется только `crystals`).

Обнуление «в начале игры»: раунда у игры нет по устройству
(`roundLifecycle` пропускается намеренно), поэтому границы, на которую можно
повесить сброс, не существует. Сбрасывать на **первом входе участника** —
там же, где `StatBridge` впервые видит его id. Явный `reset(gameId)`,
вызываемый из обработчика входа, а не побочный эффект `respawn`: после
смерти счёт обязан сохраняться, иначе накопление теряет смысл.

## 2.1. Ядро: событие убийства

`core/src/game.rs:276-283` уже кладёт в custom-событие смерти поле
`"killer": killer` (`Option<u32>`) и `"crashes"`. Значит различать «я умер»
и «меня убил вот он» можно **без правок Rust** — убийство выводится из
события жертвы.

Чего в событии нет — счёта жертвы: `score` живёт на хосте, в `StatBridge`,
а не в ядре. Поэтому:

- **не** тащить `score` в ядро (ядро не должно знать про таблицу);
- `StatBridge` держит собственную карту `gameId -> { eaten, kills, score }`
  и в обработчике `death` берёт `score` жертвы из неё же.

Правок в `core/` этот этап, скорее всего, не требует вовсе. Если по ходу
выяснится, что требуется — обязателен `npm run core:test` и пересборка
`npm run core:build` перед любой проверкой в браузере.

## 2.2. Panel (пункт 5)

Целевой состав ячеек: **логотип · съедено кристаллов · убито противников ·
общие очки**. Таймер раунда убрать — раунд бесконечен.

Хост, `src/config/game.js → panel.fields`:

- убрать `length` (визуальная награда за рост и так видна размером змейки);
- оставить `crystals` — он нужен геймплею и окну результата;
- добавить `eaten { key: 'e' }`, `kills { key: 'k' }`, `score { key: 's' }`;
- `dead { key: 'd' }` оставить без изменений — это канал окна результата;
- `activeKey: 'wa'` **оставить**: `null` здесь не вариант, панель тогда
  отправит всем клиентам литеральный ключ `'null'`.

Клиент, `src/config/client.js → modules.panel`:

- в `keys` добавить `e/k/s`, убрать `l`;
- в `fields` собрать ячейки в порядке отображения; ячейку `mode` (`wa`)
  скрыть через `style.css` тем же приёмом, каким уже скрыт `dead`.

**Две вещи проверить по коду движка до правки, обе могут молча сломать
панель:**

1. **Ключ `t`.** Комментарий в `client.js:142-145` утверждает, что `t`
   присылает сам движок и он обязан быть замаплен на поле `type: 'time'`.
   Проверить в `src/client/components/model/Panel.js` движка, что делает
   панель с ключом, которого нет в `keys`. Если игнорирует — поле `time`
   можно удалить совсем. Если падает или шумит — **оставить объявление
   поля и скрыть его в CSS**, как `dead`. Второй вариант гарантированно
   безопасен, выбирать его при любых сомнениях.
2. **Логотип.** Убедиться, что у панели есть тип ячейки под логотип
   (искать в `docs/en/client.md` движка и в `Panel.js`). Если специального
   типа нет — логотип это статический элемент разметки панели, и его место
   в `style.css` пакета, а не в `panel.fields`.

Инвариант 6 (`panelContract`) требует, чтобы каждое объявленное хостом поле
было известно клиенту, — `npm run sim` поймает рассинхрон схем сразу.

## 2.3. StatBridge: считать очки (пункты 5 и 7)

`src/host/StatBridge.js` — единственный писатель таблицы. Сейчас он пишет
`score` (= текущие кристаллы) и `deaths` (= `crashes`).

**Шаги:**

1. Завести в классе карту `gameId -> { eaten, kills, score }` и метод
   `reset(gameId)`, ставящий все три в 0.
2. `case 'crystals'`: увеличивать `eaten` и `score` на **приращение**
   съеденного, а не присваивать `total`. Ядро шлёт текущий носимый счёт —
   значит приращение считается на хосте как разница с предыдущим значением,
   и **уменьшение** (буст, смерть) в `eaten`/`score` не переносится.
3. `case 'death'`: `crystals` в панели обнуляются (как сейчас), `eaten`,
   `kills` и `score` — нет. Если в событии есть `killer` — начислить убийце
   `kills += 1` и `score += victimScore`, где `victimScore` берётся из карты
   до каких-либо изменений записи жертвы.
4. Писать в панель обеих сторон (`vimp`/`panel` из контекста `onCoreEvent`)
   и в stat (`this._stat.updateUser`) все три величины.
5. `_recordBest` перевести на `score` вместо носимых кристаллов — личный
   рекорд по общим очкам осмысленнее, чем по мгновенной длине.

**Порядок обработки важен и его нужно закрепить тестом:** начисление убийце
обязано произойти **до** обнуления записи жертвы, иначе убийство лидера
принесёт ноль.

## 2.4. Stat (пункт 7)

Хост, `src/config/game.js → stat`. Колонки резолвятся **по имени**, значит
имена можно назначить свои — но два имени трогать нельзя: `name` (никнейм) и
`latency` (пинг) заполняет сам движок. Проверить перед правкой, пишет ли
движок ещё и `status` — если да, колонку сохранить.

Целевой набор: `name` · `eaten` · `kills` · `score` · `latency`.
Все игровые — `bodyMethod: '='`: `StatBridge` сообщает итог, а не дельту,
поэтому повторное событие безвредно, а пропущенное самозалечивается.

Клиент, `src/config/client.js → modules.stat.params`:

- `columns` привести в тот же порядок, позиционно по `key`;
- `sortList.players` — сортировка по индексу колонки `score`, по убыванию;
  вторым ключом оставить `eaten` для разрешения ничьих.

## 2.5. Game over: показывать накопленные очки (пункт 2)

`src/client/gameOver.js` сейчас показывает только кристаллы на момент
смерти — их он получает закодированными в поле `dead` (`crystals + 1`).

**Шаги:**

1. Читать из панели новый ключ `s` (общие очки) в `onPanel` — механизм уже
   есть, `_lastCrystals` пополняется ровно так же.
2. Показать в карточке обе строки: «собрано в этой жизни» (из `dead - 1`) и
   «всего очков» (из `s`). Разметку добавить в `mount()`, стили — в
   `style.css`.
3. Кодировку `dead = crystals + 1` **не менять**: `+1` существует потому,
   что значения панели упираются в 0 снизу и «мёртв с нулём кристаллов»
   иначе неотличимо от «жив».
4. Обновить `tests/client/*` под новую разметку и новый ключ.
