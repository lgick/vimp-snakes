# Этап 3: снятие лимита игроков и масштабирование арены

Пункт пользователя 1. **Правит опубликованный код `vimp-engine`** — см.
раздел «Релиз» в конце.

## 3.1. Откуда берётся потолок в 8 игроков

Проверено по коду, потолков два и оба в движке:

- `packages/engine/src/master/HostRegistry.js:53` —
  `maxPlayers: toInt(maxPlayers, this._maxPlayersLimit, 1, this._maxPlayersLimit)`.
  Комната **клампится** значением `maxPlayersLimit`, приходящим из
  `packages/engine/src/config/master.js:43` (`8`, с комментарием «рамка
  P2P-плана»).
- `packages/engine/src/config/hostDefaults.js:8` — `maxPlayers: 30`, дефолт
  комнаты. Он **выше** клампа мастера, то есть сейчас не работает: любая
  комната всё равно обрезается до 8.

Поэтому поднять только `hostDefaults` бессмысленно — обрежет мастер.

## 3.2. Решение: потолок задаёт игра

Решение пользователя: **лимит задаётся только игрой и движком не
ограничивается.**

Мастер уже знает игру комнаты: `SignalingServer._onRegisterHost` получает
`gameId`/`gameVersion` и передаёт их в `HostRegistry.add`. Каталог игр у
мастера тоже есть — из него лобби берёт `roomDefaults`. Значит потолок можно
взять из манифеста игры вместо константы.

**Шаги:**

1. Найти, где мастер держит загруженные манифесты каталога, и как из них
   достать `roomDefaults.maxPlayers` по `gameId` (лобби это уже делает —
   переиспользовать тот же источник, не заводить второй).
2. `HostRegistry.add`: верхнюю границу `toInt` брать из манифеста игры
   комнаты. Оставить только санитарные рамки — целое, `>= 1`, и потолок по
   умолчанию для случая, когда `gameId` неизвестен или манифеста нет
   (комнаты старых хостов присылают `gameId: null` — этот путь уже
   предусмотрен в коде и его нельзя сломать).
3. `master.js`: `maxPlayersLimit` перестаёт быть игровым потолком. Решить
   явно и записать в комментарий — удаляется он или остаётся как санитарная
   граница для неизвестной игры. Комментарий про «рамку P2P-плана» обязан
   перестать врать.
4. `lobby.js:93` печатает лимит в консоль при старте — привести сообщение в
   соответствие с новым смыслом.
5. `hostDefaults.maxPlayers` — оставить как дефолт для игры, не объявившей
   `roomDefaults`.
6. `src/config/game.js` пакета snakes: поднять `roomDefaults.maxPlayers` до
   целевого значения игры.

**Что проверить отдельно, иначе снятие потолка окажется мнимым:** есть ли
ещё места, где число участников ограничено — валидация формы комнаты в
лобби, `HostRegistry._toPublic`, join-логика хоста. Поиск по `maxPlayers` в
`packages/engine/src` перед правкой обязателен.

**Тесты движка:** `tests/master/hostRegistry.test.js` — комната игры с
большим `roomDefaults` не обрезается; неизвестный `gameId` падает на
санитарный дефолт; мусорное значение по-прежнему санируется.

## 3.3. Вместимость карты — второй потолок, в самой игре

`src/data/maps/arena.js:39` — `RESPAWN_COUNT = 16`, и это **жёсткая
вместимость команды**: движок раздаёт точки последовательно и отказывает
следующему входящему, когда они кончились. Комментарий в файле говорит об
этом прямо. Значит поднятого лимита мало — без правки карты игроки просто
перестанут входить на 17-м.

Точек должно быть не меньше, чем `roomDefaults.maxPlayers`. Кольцо из
десятков точек одного радиуса даст слишком плотный спавн — раскладывать по
нескольким кольцам либо по спирали, с проверкой минимального расстояния
между соседями.

## 3.4. Масштабирование арены от числа участников

Радиус выводится из сетки карты **одной формулой в трёх местах**
(`arena.js`, `core/src/arena.rs`, `src/client/parts/Arena.js`):

```text
radius = cols * step * scale / 2,  centre = (radius, radius)
```

Формулу менять не нужно — нужно менять источник `SIZE`.

**Шаги:**

1. Выбрать закон масштабирования. Разумная отправная точка —
   `SIZE = base + k * sqrt(playerCount)`: площадь арены растёт линейно по
   числу игроков, то есть плотность змеек постоянна. Коэффициенты подобрать
   прогонами `growth.json` с разным числом ботов.
2. Пересчитывать `SIZE` и заново раскладывать точки респавна при изменении
   числа участников на хосте.
3. Разослать свежий `MAP_DATA`. Механика описана в комментарии
   `src/client/parts/Arena.js`: **CLEAR ключа `setId`, затем свежие
   экземпляры**. Клиентская часть уже пересчитывает радиус от полученных
   данных и правок не требует.
4. **Проверить, что ядро принимает новую карту в рантайме.** `core/src/
   arena.rs` строит `Arena::from_map` — надо убедиться, что путь `set_map`
   вызывается повторно и что живые змейки при этом не оказываются снаружи
   нового диска. Если арена **сжимается** (игрок вышел), змейка за новой
   границей должна погибнуть штатно, а не провалиться в неопределённое
   состояние.
5. Решить, с какой частотой пересчитывать. Менять геометрию на каждый вход и
   выход — значит дёргать всех при каждом подключении. Разумнее ступени
   (пересчёт при пересечении порога) и/или задержка, чтобы серия входов
   давала одну перестройку.

**Риск, который надо снять до реализации:** карта в этой игре — статический
объект модуля (`src/data/maps/arena.js`, `export default`). Пересчёт в
рантайме означает, что хост должен собирать её **функцией от числа игроков**,
а не импортировать константу. Проверить, допускает ли контракт плагина
динамический `maps` — если `GameManifest` фиксирует карты на этапе сборки,
динамический размер придётся реализовывать иначе: одна карта максимального
размера плюс переменный **игровой** радиус, который ядро и клиент получают
как часть состояния, а не как геометрию карты. Это развилка этапа, и её надо
пройти **первым** шагом — от неё зависит весь остальной объём 3.4.

## Тесты и проверки

- движок: `npx eslint . && npm test`, плюс новые тесты `HostRegistry`;
- snakes: `npm run core:test` (менялся `core/`), `npm run check:contract`,
  `npx eslint . && npm test`;
- `growth.json` с увеличенным числом ботов — арена расширяется, входят все
  боты, инварианты зелёные, `--determinism` проходит;
- браузер: три и более вкладок, вход/выход на границе ступени, никто не
  оказывается за границей после перестройки.

## Релиз

Правится `packages/engine/src/master/`, `src/config/master.js` и
`src/config/hostDefaults.js` — всё это входит в `files` пакета
`vimp-engine`. Обязательна запись в `packages/engine/CHANGELOG.md` под
`## [Unreleased]`:

- `### Changed`, если снятие потолка не отвергает ни одну ранее валидную
  конфигурацию (ожидаемый случай — потолок только повышается);
- `### ⚠️ Breaking` + `### Migration`, если игра без `roomDefaults` начнёт
  отвергаться там, где раньше принималась.

Версию не редактировать и не публиковать. Если правится крейт — за движком
обязан пойти `vimp-tanks`.
